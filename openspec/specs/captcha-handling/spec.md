# captcha-handling Specification

## Purpose
Не обрывать рассылку откликов, когда API hh отвечает `captcha_required`.

## Requirements

### Requirement: Перенос кук после решения каптчи

После решения каптчи в браузере Playwright куки контекста SHALL переноситься в джар HTTP-сессии кликера независимо от типа джара (MozillaCookieJar/HHOnlyCookieJar или requests-джар). Отсутствие домена у куки SHALL NOT прерывать перенос. Проверяется `tests/test_captcha_cookies.py`.

#### Scenario: Джар сессии — MozillaCookieJar

- **WHEN** каптча решена и сессия использует HHOnlyCookieJar без метода `.set()`
- **THEN** куки переносятся через `set_cookie`, ошибки `'HHOnlyCookieJar' object has no attribute 'set'` нет

#### Scenario: Куки чужих доменов

- **WHEN** среди кук браузера есть домены не hh
- **THEN** HHOnlyCookieJar их отбрасывает, куки hh сохраняются

### Requirement: Каптча решается от имени аккаунта

Решение каптчи SHALL выполняться в браузерном контексте с куками аккаунта, чья сессия получила `captcha_required`. Опыт 30.09.2026: каптча, решённая вручную в браузере с куками аккаунта, снимает блокировку — повтор отклика и следующий отклик проходят.

> Известный дефект на 30.09.2026: `_solve_captcha_async` открывает каптчу в пустом контексте без кук, распознаёт её слабой моделью и не проверяет, принят ли ответ. Исправляется отдельным изменением.

#### Scenario: Правильный ответ

- **WHEN** API вернул `captcha_required` и каптча решена верно в контексте с куками аккаунта
- **THEN** повтор того же отклика принимается API без новой каптчи
